Slide decks are powered by
[astromotion](https://github.com/ANUcybernetics/astromotion), a thin Astro
integration over Reveal.js with a Marp-inspired markdown syntax. The theme
registers astromotion for you when you opt in, and ships a deck stylesheet that
matches the rest of the theme --- it derives its palette from the same brand
tokens, so a re-branded site gets re-branded decks for free.

A deck is a `.deck.mdx` file under `src/decks/`. Each file becomes a route at
`/decks/<name>`, and slides are separated by `---` thematic breaks. There's a
complete, live example at [`/decks/astromotion`](/decks/astromotion) — the
source for it lives at `docs/src/decks/astromotion.deck.mdx`.

## Setup

Add astromotion alongside the theme in `astro.config.ts` and point it at a deck
stylesheet that imports the theme's deck styles:

```ts
import { defineConfig } from "astro/config";
import universityTheme from "astro-theme-university";
import { astromotion } from "astromotion";

export default defineConfig({
  integrations: [
    universityTheme(),
    astromotion({ theme: "./src/decks/theme.css" }),
  ],
});
```

```css
/* src/decks/theme.css */
@import url("astro-theme-university/styles/deck.css");
```

The deck stylesheet carries the brand tint scales and the slide classes below,
plus a full-bleed `logo-slide` class and reveal animations for closing logo
slides.

## Composing decks with `@include`

There is a single mechanism for pulling shared content into a deck: the
`@include` directive, written as a JSX comment.

```mdx
{/* @include ./partials/intro.mdx */}
```

`@include` runs before slides are split, so a `---` inside an included file
starts a new slide. The included file's YAML frontmatter is stripped
automatically, which means the same file can render both as a standalone page
and as deck slides. Paths can be relative to the deck, or bare module specifiers
resolved from your `node_modules` --- so a package (a branding package, say) can
ship shared partials that any deck includes without a relative path. Only `.mdx`
files can be included.

## Two ways to organise reusable content

The include mechanism is the same either way; what differs is where the fragment
lives and whether it has a life of its own outside the deck.

### Content-collection topics

On a course site, a _topic_ is a content-collection entry that doubles as a deck
slide. It's browsable on its own at `/topics/<slug>/`, participates in the
content graph via its `related` edges, and is pulled into a lecture by including
it from the collection directory:

```mdx
{/* @include ../content/topics/variables.mdx */}
```

Reach for this when the fragment is genuinely course content — something a
student might read standalone as well as see on a slide.

### Deck partials

When a fragment is pure slide furniture — an opening acknowledgement, a
presenter roster, a closing logo — it doesn't belong in a content collection.
Keep it as a deck-only partial under `src/decks/partials/` and include it by
relative path:

```mdx
{/* @include ./partials/ack-country.mdx */}
```

This is the pattern for "master" decks that share a common opening and closing
across several variants of a talk: each master deck includes the same handful of
partials and adds its own middle.

## Slide features

A quick reference — the [example deck](/decks/astromotion) demonstrates each
one:

- **slide classes**: `{/* _class: impact */}` (available: `impact`, `hero`,
  `quote`, `centered`)
- **backgrounds**: `![bg](./assets/photo.avif)`,
  `![bg right:40%](./assets/side.avif)`,
  `![bg brightness:0.5 blur:2px](./assets/dark.avif)`
- **speaker notes**: a fenced ` ```notes ` block, authored in markdown (press
  **S** in the deck)
- **authoring comments**: a fenced ` ```comment ` block --- prose for whoever
  edits the deck next, stripped from the rendered deck
- **code blocks**: fenced code blocks get syntax highlighting automatically
- **QR codes**: `![qr](https://example.com)`

Co-locate background and other deck images under `src/decks/assets/` and
reference them with a relative path. astromotion copies everything under
`src/decks/` (except the deck and CSS files) into the build output, so
co-located assets resolve in production; images elsewhere in `src/` won't be
copied.

## Artwork behind every impact slide

`![bg](…)` dresses one slide at a time. To give _every_ `impact` slide the same
full-bleed artwork instead of the flat brand fill, set it once in your deck
stylesheet. For an asset sitting beside that stylesheet, declare
`background-image` on the class directly, so your bundler hashes and
base-prefixes it like any other deck asset:

```css
.reveal section.impact {
  background-image: url("./assets/impact-bg.avif");
}
```

For a URL that needs no bundler resolution --- a `public/` path, an absolute
URL, a data URI --- use the custom property instead:

```css
:root {
  --at-deck-impact-bg-image: url("/decks/impact-bg.avif");
}
```

(The two forms exist for the same reason as astromotion's whiteboard background:
a relative `url()` inside a custom property resolves against wherever the
`var()` is _used_, not where it's declared, which lightningcss rejects as
ambiguous.)

The image is sized like a `cover` background and nothing dims or scrims it, so
it's on you to supply artwork that impact slides' white text stays legible over
--- a dark or low-contrast ground, or a mostly-empty field with the motif kept
to a corner.

## Table headers

Decks style tables from their own tokens rather than the `--at-table-header-*`
pair the web side uses. The web treatment is a solid brand fill with white text,
which works on a light page but on a near-black slide becomes the
highest-contrast object on it. Decks instead tint the header cells and colour
the text with the brand colour:

```css
:root {
  --at-deck-table-header-bg: rgb(from var(--at-primary) r g b / 14%);
  --at-deck-table-header-text: var(--at-primary);
  --at-deck-table-header-rule: rgb(from var(--at-primary) r g b / 55%);
}
```

The tint applies to every `th`, not just the ones in `thead`. A matrix --- a
table whose body rows carry `<th scope="row">` labels, like a grid of counts
with words down the side and across the top --- has two header axes that mean
the same thing, and filling only the top one implies a hierarchy the markup
doesn't have. Ordinary tables are unaffected, since they have no body headers;
the `--at-deck-table-header-rule` underline is what still marks a true header
row.
