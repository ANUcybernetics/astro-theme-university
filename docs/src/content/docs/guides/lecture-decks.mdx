Slide decks are powered by
[astromotion](https://github.com/ANUcybernetics/astromotion), a thin Astro
integration over Reveal.js with a Marp-inspired markdown syntax. astromotion is
a separate package that you install and register beside the theme; the theme
ships a deck stylesheet that matches the rest of the site. It derives its
palette from the same brand tokens, so a re-branded site gets re-branded decks
for free.

A deck is a `.deck.mdx` file under `src/decks/`. Each file becomes a route at
`/decks/<name>`, and slides are separated by `---` thematic breaks. There's a
complete, live example at [`/decks/astromotion`](/decks/astromotion) --- the
source for it lives at `docs/src/decks/astromotion.deck.mdx`.

## Setup

Install astromotion beside the theme and turn on `decks`:

```ts
import { defineConfig } from "astro/config";
import universityTheme from "astro-theme-university";

export default defineConfig({
  integrations: [universityTheme({ decks: true })],
});
```

The theme registers astromotion with its own deck stylesheet and body font, and
appends astromotion's remark plugins (slide splitting, `@include`, the `_class`
and `![bg]` directives) to the markdown chain it owns. Pass an object to forward
astromotion options: `routePrefix` to mount decks somewhere other than `/decks`,
or `theme` for a site that layers deck CSS of its own over the theme's:

```ts
universityTheme({ decks: { theme: "./src/decks/theme.css" } });
```

```css
/* src/decks/theme.css */
@import url("astro-theme-university/styles/deck.css");
```

A site that registers `astromotion()` itself keeps doing so; `decks` then warns
and steps aside, and the site passes `extraRemarkPlugins: deckRemarkPlugins` to
the theme as before.

The deck stylesheet carries the brand tint scales and the slide classes below,
plus a full-bleed `logo-slide` class and reveal animations for closing logo
slides.

## Composing decks with `@include`

There is a single mechanism for pulling shared content into a deck: the
`@include` directive, written as a JSX comment.

```mdx
{/* @include ./partials/intro.mdx */}
```

`@include` runs before slides are split, so a `---` inside an included file
starts a new slide. The included file's YAML frontmatter is stripped
automatically, which means the same file can render both as a standalone page
and as deck slides. Paths can be relative to the deck, or bare module specifiers
resolved from your `node_modules`. A package (a branding package, say) can then
ship shared partials that any deck includes without a relative path. Only `.mdx`
files can be included.

## Two ways to organise reusable content

The include mechanism is the same either way; what differs is where the fragment
lives, and whether it has a life beyond the deck.

### Content-collection topics

On a course site, a _topic_ is a content-collection entry that doubles as a deck
slide. It's browsable on its own at `/topics/<slug>/` and participates in the
content graph via its `related` edges. It's pulled into a lecture by including
it from the collection directory:

```mdx
{/* @include ../content/topics/variables.mdx */}
```

Reach for this when the fragment is genuinely course content --- something a
student might read standalone as well as see on a slide.

### Deck partials

When a fragment is pure slide furniture --- an opening acknowledgement, a
presenter roster, a closing logo --- it doesn't belong in a content collection.
Keep it as a deck-only partial under `src/decks/partials/` and include it by
relative path:

```mdx
{/* @include ./partials/ack-country.mdx */}
```

This is the pattern for "master" decks that share a common opening and closing
across several variants of a talk. Each master deck includes the same handful of
partials and adds its own middle.

## Slide features

A quick reference --- the [example deck](/decks/astromotion) demonstrates each
one:

- **slide classes**: `{/* _class: impact */}` (available: `impact`, `hero`,
  `quote`, `centered`)
- **backgrounds**: `![bg](./assets/photo.avif)`,
  `![bg right:40%](./assets/side.avif)`,
  `![bg brightness:0.5 blur:2px](./assets/dark.avif)`
- **speaker notes**: a fenced ` ```notes ` block, authored in markdown (press
  **S** in the deck)
- **authoring comments**: a fenced ` ```comment ` block --- prose for whoever
  edits the deck next, stripped from the rendered deck
- **code blocks**: fenced code blocks get syntax highlighting automatically
- **QR codes**: `![qr](https://example.com)`

Co-locate background and other deck images under `src/decks/assets/` and
reference them with a relative path. astromotion copies everything under
`src/decks/` into the build output except source files (`.mdx`, `.md`, `.svelte`
and `.css`), so co-located assets resolve in production. Images elsewhere in
`src/` won't be copied.

## Artwork behind every impact slide

`![bg](…)` dresses one slide at a time. To give _every_ `impact` slide the same
full-bleed artwork instead of the flat brand fill, set it once in your deck
stylesheet. For an asset sitting beside that stylesheet, declare
`background-image` on the class directly, so your bundler hashes and
base-prefixes it like any other deck asset:

```css
.reveal section.impact {
  background-image: url("./assets/impact-bg.avif");
}
```

For a URL that needs no bundler resolution --- a `public/` path, an absolute
URL, a data URI --- use the custom property instead:

```css
:root {
  --at-deck-impact-bg-image: url("/decks/impact-bg.avif");
}
```

(The two forms exist for the same reason as astromotion's whiteboard background.
A relative `url()` inside a custom property resolves against wherever the
`var()` is _used_, not where it's declared. lightningcss rejects that as
ambiguous.)

The image is sized like a `cover` background, and nothing dims or scrims it.
Supply artwork that keeps the slide's text legible: a low-contrast ground, or a
mostly-empty field with the motif kept to a corner. Which ink that text takes
depends on the brand colour (white on a dark `--at-primary`, near-black on a
light one; see `--at-on-primary`), so match the artwork to it.

## The hero scrim

A `hero` slide dims its background image behind the title with a scrim that runs
from 20% black at top to 80% at bottom. Retint or restrength it through
`--at-deck-hero-scrim`, which takes any CSS image:

```css
:root {
  --at-deck-hero-scrim: url("/decks/hero-scrim.png");
}
```

The default scrim is a tiny PNG with an alpha channel (a 1x256 ramp stretched
over the slide), not a CSS gradient. An override should be a raster image with
alpha too. The reason is PDF export. Chrome writes a gradient whose alpha varies
as a shading behind a soft mask. Ghostscript (the compressor behind
`astromotion-pdf`) hollows that mask out, so the exported deck silently prints
white titles on undimmed artwork. An opaque gradient under
`mix-blend-mode: multiply` survives Ghostscript, but macOS Preview, Safari and
Quick Look draw it wrong: too bright before compression, near-uniform darkening
after. An image with an alpha channel is the one kind of transparency every PDF
writer and renderer agrees on. So don't put a translucent gradient, a
`mask-image` or a blend mode in the override. The browser will show the slide
you designed, but the exported PDF won't match it. (An opaque gradient exports
fine, but it covers the artwork entirely, so it only makes sense on a hero with
no background image.)

## Table headers

Decks style tables from their own tokens rather than the `--at-table-header-*`
pair the web side uses. The web treatment is a solid brand fill with white text.
That works on a light page, but on a near-black slide it becomes the
highest-contrast object in view. Decks instead tint the header cells and colour
the text with the brand colour:

```css
:root {
  --at-deck-table-header-bg: rgb(from var(--at-primary) r g b / 14%);
  --at-deck-table-header-text: var(--at-primary);
  --at-deck-table-header-rule: rgb(from var(--at-primary) r g b / 55%);
}
```

The tint applies to every `th`, not just the ones in `thead`. A matrix table has
body rows carrying `<th scope="row">` labels --- think a grid of counts with
words down the side and across the top. Its two header axes mean the same thing,
so filling only the top one would imply a hierarchy the markup doesn't have.
Ordinary tables are unaffected, since they have no body headers; the
`--at-deck-table-header-rule` underline is what still marks a true header row.
